# 构建基础IAP流程：提供串口接收Bin文件并写入Flash的完整实现方法

1. **启动流程**：系统复位后先执行Bootloader程序，完成基础硬件初始化。随后检测升级标志，决定进入固件更新或跳转至APP应用区执行。
2. **串口接收**：通过串口协议接收Bin文件数据，利用DMA与空闲中断提升接收效率。数据暂存缓冲区，等待后续写入Falsh存储区。
3. **Flash写入**：在写入前需擦除目标扇区，确保满足编程条件。按半字或字节方式将接收到的Bin数据写入指定Falsh地址空间。
4. **程序跳转**：跳转前校验APP入口地址的有效性，设置主堆栈指针MSP。最后通过函数指针调用复位向量，实现到应用程序的安全跳转。

## IAP（In-Application Programming，应用内编程）

<p style="text-indent:2em;">IAP是指程序运行过程中，由MCU自己控制擦除和重写内部Flash，完成固件升级</p>

### 特点 

- 不需要外部工具，MCU自己通过程序控制Flash操作。
- 常用于远程升级、无线升级（OTA）、U盘升级等。
- 需要特别小心处理Flash写保护、掉电恢复机制。
- 通常会将 IAP Bootloader 程序放在一段固定的 Flash 地址，比如 0x08000000，然后应用程序放在后面。

### 常规应用

- 在线远程升级（比如 WiFi/4G/蓝牙设备固件更新）。
- 本地脱机升级（比如通过 SD卡、U盘插入设备自动升级）。

## STM32三种启动模式

<p style="text-indent:2em;">在系统复位后，SYSCLK的第4个上升沿，BOOT引脚的值将被锁存。用户可以通过设置BOOT1和BOOT0引脚的状态来选择在复位后的启动模式。</p>

<p style="text-indent:2em;">从待机模式退出时，BOOT引脚的值将被重新锁存。因此，在待机模式下BOOT引脚应保持为需要的启动配置。</p>

<p style="text-indent:2em;">在启动延迟之后，CPU从地址0x00000000获取堆栈顶地址，并从启动存储器的0x00000004指示的地址开始执行代码。三种启动模式其实就是将各自存储空间的地址映射到0x00000000中。</p>

| BOOT1 | BOOT0 | 启动模式     | 地址映射   |
| ----- | ----- | ------------ | ---------- |
| X     | 0     | 主闪存启动   | 0x08000000 |
| 0     | 1     | 系统内存启动 | 0x1FFFF000 |
| 1     | 1     | SRAM启动 | 0x20000000 |

- **主闪存启动**：执行用户应用程序，适用于正常的工作模式。该模式下程序掉电不丢失，是产品发布后的标准运行模式。
- **系统内存启动**：运行厂商预制的Bootloader。常用于通过UART等接口进行ISP固件烧录，实现无需调试器的程序更新。
- **SRAM启动**：用于调试或临时运行程序。断电后内容丢失，适合验证代码逻辑而不影响Flash存储。

## 系统复位

<p style="text-indent:2em;">除了数字控制器的RCC_CSR寄存器中的复位标志位和备份区域中的寄存器以外，系统复位将复位所有的寄存器至它们的复位状态。当发生以下任一事件时，产生一个系统复位：</p>

- NRST引脚上的低电平（外部复位）
- 窗口看门狗计数终止（WWDG复位）
- 独立看门狗计数终止（IWDG复位）
- 软件复位（SW复位）
- 低功耗管理复位

<p style="text-indent:2em;">可通过查看RCC_CSR控制状态寄存器中的复位状态标志位识别复位事件来源</p>

## .bin文件内容

- 中断向量表（4字节对齐，64字节）

    - RAM起始地址
    - 复位中断（写入Flash地址+4）

- 函数代码（指令码）
- 常量字符串
- 全局变量初始值

## 系统Bootloader

- 通过控制BOOT0和BOOT1引脚电平进入到Bootloader模式中
- 使用串口完成数据的烧录。串口波特率默认为115200，使用偶校验，数据位为8，停止位为1。
- 存储位置特殊：0x1FFFF000

## 自定义Bootloader

- 程序本身存放的位置不同，Flash中地址是起始地址0x08000000。

    - 程序冲突问题：Bootloader程序和执行的Application程序需要存放到不同的位置
    - AB分区存放，B区一定要存放在Flash起始的位置
    - 一般给Bootloader留有足够的空间和余量（16KB）。

- 复位之后永远执行的是B程序

    - 执行A程序需要手动跳转
    - 即使B程序和A程序的代码是完全连号的也不会执行A程序
    - 只能在B程序中执行A程序的复位中断（Flash地址+4）

- 功能：串口接收程序数据，写入Flash对应位置中。

### （1）USART串口通信
<p style="text-indent:2em;">发送方：使用串口将整个程序分批多次发送，一次发送256个字节，发送方需要中间延时（给Bootloader程序时间写入到Flash）。</p>

<p style="text-indent:2em;">接收方：使用接收中断的方式，接收发送方发送的分片程序，并将程序写入到片上Flash的对应区域。</p>

> 在串口接收的过程中出现丢包问题，通过修改串口波特率为9600以及增大发送方发送间隔临时解决。最终诊断是由于接收回调函数中使用了串口打印导致阻塞，将串口打印移至外部解决。

### （2）片上Flash写入

#### Flash擦除

<p style="text-indent:2em;">先擦除再写入，擦除按页擦除。默认Flash为加锁状态，需要优先解锁，使用完成之后重新加锁。</p>

1. 解锁Flash
2. 遍历需要写入的地址的值，如果出现不为0xFF的情况，擦除该地址所在页。
3. 重锁Flash

> 注：  
> <p style="text-indent:2em;">USART每接收一次数据触发中断，中断中得到接收到的数据长度，该长度用于遍历。</p>
> <p style="text-indent:2em;">擦除只能按页擦，故需要计算该页的起始地址。</p>
> <p style="text-indent:2em;">需要使用全局变量存储当前偏移量</p>
> <p style="text-indent:2em;">读取地址中的值最好使用volatile关键字</p>


#### Flash写入

<p style="text-indent:2em;">只支持16位、32位、64位写入，写入默认小端序。</p>
<p style="text-indent:2em;">遍历接收到的内容，按每个字节拼接为半字（16位）后写入到Flash中，更新偏移量，当末尾只有一个字节的时候不能拼接一个半字写入会影响下一个字节的正确写入，将以前保存的最后一个多余字节（如果有的话），拼接到下一组数据的首部，当然下一组数据也要判断。</p>

> 问题：擦除和写入都需要时间，所以分多字节延时发送间隔要稍微大一些，负责会丢包。  
> 解决方法：增大缓冲区，换一个高速稳定的通信协议，降低波特率，提前一次性擦除需要写入的区域。

### （3）跳转程序

1. 编写启动跳转逻辑：按键或超时判断。
2. 校验A程序栈顶地址与复位中断地址是否合法
3. 注销Bootloader程序：关中断、设置堆栈指针、重定向中断向量表
4. 跳转到A程序复位中断
```C
uint32_t app_reset_handle = *(volatile uint32_t*)(APP_START_ADDR + 4);
typedef void (*pFubc)(void);
pFunc jump_to_App = (pFunc)app_reset_handle;
jump_to_App();
```
5. 在A程序开头：关闭中断、重定向中断向量表、开启中断
```C
__disable_irq();
SCB->VTOR = APP_START_ADDR;
__enable_irq();
```


# 引入可靠性机制：外置Flash存储、更新标志位管理与CRC校验策略

1. **OTA标志管理**：结合EEPROM或内部备份区保存OTA标志与版本信息，确保升级状态持久化，支持断电续传。
2. **外置Flash存储**：通过外置Flash存储新固件，利用SPI接口实现高速读写，支持大容量程序更新，缓解片内资源压力。
3. **启动模式检测**：系统启动时检测升级标志位，判断是否进入升级模式，保证流程可控与正确引导。
4. **CRC32数据校验**：传输完成后执行CRC32校验，与发送端比对，校验失败则禁止写入，防止错误写入导致程序损坏。

## OTA标志管理

### （1）编写EEPROM（W25Q32）驱动
> 详见 Bootloader\Driver\W24C02\W24C02.h 和 Bootloader\Driver\W24C02\W24C02.c
### （2）在指定区域添加更新标志
```C
// 是否需要更新状态
#define CHECK_UPDATE_ADDR 0x10 // 存储更新状态的位置
#define BOOT_UPDATE 0x01       // 需要更新
#define BOOT_NO_UPDATE 0x02    // 不需要更新
#define BOOT_RESET 0x03        // 恢复出厂设置

// 校验密钥
#define CHECK_KEY_ADDR 0x11 // 存储校验密钥的位置
#define CHECK_KEY 0x486A    // 密钥值
```
<p style="text-indent:2em;">为防止更新标志被以外更改，每次更改更新标志需要检查密钥。只有在密钥正确的情况下才允许读取更新标志位。</p>
<p style="text-indent:2em;">这种写法的原理是：因为EEPROM的内容可能被以外修改，如果更新标志位被以外修改，密钥的值大概率也会被以外修改导致密钥校验不通过而不更新。但是如果刚好更新标志位被以外修改且密钥没被修改还是会出现以外更新。当然这种情况的概率很低。</p>

# 整合OTA升级全流程：从触发条件检测到固件验证、安装与系统重启的工程化实践

1. **触发条件**：通过标志位、定时任务或远程指令触发OTA升级流程。启动时Bootloader优先检查更新标志，决定进入升级模式还是跳转至APP程序。
2. **固件下载****：利用Wi-Fi、4G或以太网连接服务器安全下载新固件。支持断点续传与分包传输，确保弱网络环境下的数据完整性与通信稳定性。
3. **验证机制**：下载完成后进行CRC32或SHA校验，防止损坏或篡改的固件被写入。验证失败则保留原版本并上报错误日志，保障系统运行安全。
4. **安装写入**：解锁Flash后按扇区擦除目标区域，将新固件写入指定地址。采用双分区的机制避免升级过程中系统无法启动的风险。

# 实现APP安全启动的核心原理

- **向量表定位**：STM32启动时从固定地址读取中断向量表，首项为栈顶指针，次项为复位向量。Bootloader通过修改向量表或跳转至APP区起始地址，实现程序控制权转移。
- **堆栈指针重置**：跳转前必须将主堆栈指针（MSP）更新为APP的初始值，确保后续函数调用不崩溃。该操作通过读取APP向量表首地址并调用__set_MSP实现。
- **安全跳转流程**：跳转前需验证APP区域的有效性，防止非法地址执行。典型流程包括判断标志位、设置MSP、获取入口函数并执行，确保系统稳定启动。
